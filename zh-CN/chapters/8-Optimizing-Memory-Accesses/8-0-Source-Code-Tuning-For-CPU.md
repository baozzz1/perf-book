# 第二部分：源代码调优

在本书第一部分中，我们讨论了如何发现代码中的性能瓶颈。在第二部分中，我们将探讨如何通过低级源代码优化（low-level source code optimization）技术（也称为*调优*）来修复这些瓶颈。

现代 CPU 是非常复杂的设备，几乎不可能预测某段代码的运行速度。软件和硬件的性能取决于许多因素，各个影响因子数量之多，远超人脑所能掌握的范围。幸运的是，借助我们在本书第一部分讨论的各种性能监控能力，可以从 CPU 视角观察代码的运行情况。我们将广泛依赖之前学到的方法和工具来指导我们的性能工程过程。

从宏观角度来看，软件优化可以分为五大类：

* **算法优化（Algorithmic optimizations）**：分析程序中使用的算法和数据结构，寻找更优的替代方案。例如：用快速排序替代冒泡排序。
* **并行化计算（Parallelizing computations）**：如果算法高度可并行化，可以将程序改为多线程，或考虑在 GPU 上运行。目标是同时执行多项任务。并发已经在硬件和软件栈的所有层次中得到应用。例如：将工作分配到多个线程；在数据中心中平衡多台服务器的负载；使用异步 IO 避免等待 IO 操作时阻塞；保持多个并发网络连接以重叠请求延迟。
* **消除冗余工作（Eliminating redundant work）**：不做不需要做的工作，或不重复做已经做过的工作。例如：利用更多 RAM 来减少 CPU 和 IO 使用量（缓存、查找表、压缩）；预先计算编译期已知的值；将循环不变计算移到循环之外；通过引用传递 C++ 对象，以避免按值传递导致的大量拷贝。
* **批处理（Batching）**：将多个类似操作聚合后一次性执行，从而降低多次重复操作的开销。例如：发送大 TCP 数据包而非许多小包；分配一大块内存而非为数百个小对象逐个分配空间。
* **排序（Ordering）**：重新排列算法中的操作顺序。例如：改变数据布局以实现顺序内存访问；根据类型对 C++ 多态对象数组进行排序，以更好地预测虚函数调用；将热点函数分组并在二进制文件中彼此靠近放置。

本书讨论的许多优化都属于多个类别。例如，向量化（vectorization）可以看作并行化和批处理的结合；循环分块（loop blocking，即 tiling）则是批处理和消除冗余工作的体现。

为了完整起见，我们还列出一些可能显而易见但仍然合理的加速方法：

* **用另一种语言重写代码**：如果程序使用解释型语言（Python、JavaScript 等）编写，可以将其性能关键部分用开销更小的语言重写，例如 C++、Rust、Go 等。
* **调整编译器选项**：确保至少使用以下三个编译器标志：`-O3`（启用与机器无关的优化）、`-march`（启用针对特定 CPU 架构的优化）、`-flto`（启用过程间优化）。但不要止步于此，还有许多其他影响性能的选项。我们将在后续章节中介绍其中一些。您可以考虑为应用程序挖掘最佳选项集合，市面上有自动执行此过程的商业产品。
* **优化第三方软件包**：绝大多数软件项目都依赖多层专有和开源代码，包括操作系统、库和框架。可以通过替换、修改或重新配置其中某些部分来寻求改进。
* **购买更快的硬件**：显然，这是一个有成本的商业决策，但有时这是在其他选项已经穷尽后唯一能提升性能的方法。当您识别出应用程序中的性能瓶颈并清楚地向上级管理层传达时，更容易为采购提供依据。例如，一旦发现内存带宽限制了多线程程序的性能，您可以建议购买具有更多内存通道和 DIMM 插槽的服务器主板和处理器。

### 算法优化

标准算法和数据结构并不总是适合对性能要求苛刻的工作负载。例如，传统上，链表的每个新节点都是动态分配的。除了可能引发大量昂贵的内存分配之外，这很可能导致链表中所有元素分散在内存中的不同位置。遍历这样的数据结构对缓存不友好。即使算法复杂度仍然是 O(N)，实际运行时间也会比普通数组差得多。某些数据结构（如二叉树）天然具有类似链表的表示方式，因此可能会诱使人以指针追踪（pointer-chasing）的方式实现它们。然而，存在更高效的"扁平化（flat）"版本，例如 `boost::flat_map` 和 `boost::flat_set`。

在为某个问题选择算法时，您可能会很快选择最流行的方案然后继续……即使它未必是您特定情况下的最优选择。假设您需要在有序数组中查找元素。大多数开发者第一个想到的是二分搜索，对吧？它非常知名，在算法复杂度方面也是最优的，O(logN)。如果我告诉您数组存储的是 32 位整数值，且数组大小通常很小（不超过 20 个元素），您会改变决定吗？最终，测量应该指导您的决策，但二分搜索受分支预测失误（branch mispredictions）的影响，因为每次元素值的判断都有 50% 的可能为真。这就是为什么在小数组上，即使线性扫描的算法复杂度更差，通常也更快。[^1]

### 数据驱动开发（Data-Driven Development）

数据驱动开发（DDD）的核心思想是研究程序如何访问数据：数据在内存中的布局方式，以及在程序中如何转换；然后据此修改程序（改变数据布局，改变访问模式）。这种方法的经典示例是结构体数组（Array-of-Structures，AOS）到数组结构体（Structure-of-Array，SOA）的转换，如代码清单 AOStoSOA 所示。

代码清单：SOA 与 AOS 转换。

```cpp
// Array of Structures (AOS)             // Structure of Arrays (SOA)
struct S {                               struct S {
  int a;                                   int a[N];
  int b;                        <=>        int b[N];
  int c;                                   int c[N];
  // other fields                          // other arrays
};                                       };
S s[N];                                  S s;
```
哪种布局更好，取决于代码访问数据的方式。如果代码遍历数据结构 `S` 并且只访问字段 `b`，则 SOA 更好，因为所有内存访问都是顺序的。然而，如果程序遍历数据结构并对对象的所有字段进行*大量*操作，则 AOS 可能提供更好的内存带宽利用率，某些情况下性能更好。在 AOS 场景中，结构体成员很可能位于同一缓存行（cache line），因此需要读取的缓存行更少，也占用更少的缓存空间。但更多时候，SOA 能提供更好的性能，因为它使其他重要转换（例如向量化）成为可能。

数据驱动开发的另一个广泛示例是小尺寸优化（small-size optimization）。其思想是静态预分配一定量的内存以避免动态内存分配。对于元素数量上限可以很好预测的中小型容器，这种方法特别有用。现代 C++ STL 中 `std::string` 的实现将前 15--20 个字符保存在栈内存分配的内部缓冲区中，仅对更长的字符串才在堆上分配内存。这种方法的其他实例可以在 LLVM 的 `SmallVector` 和 Boost 的 `static_vector` 中找到。

### 低级优化（Low-Level Optimizations）

性能工程是一门艺术。和任何艺术一样，可能的场景是无穷无尽的。不可能涵盖所有可以想到的各种优化。第二部分的各章主要介绍针对现代 CPU 架构的优化。

在深入介绍具体的源代码调优技术之前，有几点注意事项需要说明。首先，避免对低质量的代码进行调优。如果一段代码存在高层次的性能低效问题，不应该对其应用机器特定的优化。始终优先修复主要问题。只有在确认算法和数据结构对于您要解决的问题已经是最优的情况下，才应该尝试应用低级改进。

其次，请记住，您实现的优化可能并不在每个平台上都有益。例如，[LoopOptsHighLevel] 中讨论的循环分块（Loop Blocking，即 tiling），取决于系统内存层次结构的特性，尤其是 L2 和 L3 缓存大小。因此，针对具有特定 L2 和 L3 缓存大小的 CPU 调优的算法，在缓存较小的 CPU 上可能效果不佳。重要的是在应用程序将要运行的平台上测试更改。

接下来的四章按照 TMA 分类（参见 [TMA]）组织：

* [MemBound]：优化内存访问——`TMA:MemoryBound` 类别。
* [CoreBound]：优化计算——`TMA:CoreBound` 类别。
* [ChapterBadSpec]：优化分支预测——`TMA:BadSpeculation` 类别。
* [secFEOpt]：机器代码布局优化——`TMA:FrontendBound` 类别。

这种分类背后的思想是为开发者在使用 TMA 方法进行性能工程工作时提供一个检查清单。每当 TMA 将性能瓶颈归因于上述某个类别时，请参阅相应章节了解您的选项。

[ChapterOtherTuning] 涵盖与前四章中任何类别都不特别相关的优化主题。在该章中，我们将讨论特定于 CPU 的优化，审视几个与微架构相关的性能问题，探索用于优化低延迟应用程序的技术，并为系统调优提供建议以获得最佳性能。

[secOptMTApps] 涉及优化多线程应用程序中的一些常见问题。它提供了五个真实世界多线程应用程序的案例研究，解释了为什么它们的性能无法随 CPU 线程数的增加而扩展。我们还讨论了缓存一致性（cache coherency）问题，例如"伪共享（False Sharing）"以及一些专为分析多线程应用程序设计的工具。
